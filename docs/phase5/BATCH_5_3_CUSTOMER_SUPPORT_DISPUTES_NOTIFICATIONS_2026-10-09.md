## Scope and decisions

- Introduced owner-scoped **general support cases** and append-only **encrypted support messages**, deliberately separate from financial transaction disputes and refund authorizations. Subject and message text are encrypted using the existing TwiPay data encryption key; neither is stored in operation audit event state or notification content. No password/PIN/identity uploads are requested or accepted.
- `packages/database/prisma/migrations/0016_customer_support_conversations` adds two tables, foreign keys, statuses, a maximum-width category constraint, idempotency keys and database triggers protecting message immutability and closed case state. Adds granular `ops.support.read` and `ops.support.reply` RBAC permissions; only OPERATIONS and SUPER_ADMIN may reply; COMPLIANCE has support-read only. No changes to immutable ledger, holds, fees, refund execution or default-off financial flags.
- Customer session-protected endpoints: `POST/GET /v1/support/cases`, `GET /v1/support/cases/:reference`, `POST /v1/support/cases/:reference/replies`. Customer identity is always obtained from server-side sessions; case lookup and row locks scope by `userId`. Strict body shapes/categories/lengths, UUID request keys and bounded result sets. Case creation is serialized by a lock on the customer user row, with a five-new-case rolling-24-hour cap. Existing message caps prevent a case exceeding 100 messages; mutation rate limits apply separately (8/minute per configured local bucket). Unknown, foreign or closed cases fail closed. Request-key replay returns an existing result only for matching original actor, case and content; otherwise rejects.
- Administrator endpoints at `/v1/operations/support/cases*` are behind the existing session and PermissionGuard, with recent MFA for case listing, detail and mutations. Reply and close events are audited using actor IDs, state and reference only, not private message text. Staff notification is an existing encrypted email-outbox record containing **only a generic login reminder**; it requires an authoritative email-verification timestamp and never assumes delivery. Customer support conversations themselves provide secure reply history; this batch **does not** invent an in-app read/unread notification inbox.
- Financial disputes: a new **read-only** `GET /v1/operations/disputes` list guarded by `ops.disputes.review` and recent MFA, alongside the existing protected dispute-detail endpoint. The admin support page shows non-sensitive dispute status summaries. It **does not** grant monetary modification, refunds, ledger alteration, evidence upload or support-to-refund escalation.
- Original ErhaPay React/Vite `apps/customer-ui` remains the release customer design. The existing `/dashboard/settings/support-centre` foundation now supports general cases and replies; `/dashboard/settings/support` remains the independent financial dispute form. The existing notification history still displays delivery metadata, not fake message read receipts. Admin functionality resides only in the separate restricted `apps/admin/app/support` surface. Legacy `apps/web` remains a reference, not an active customer UI.
