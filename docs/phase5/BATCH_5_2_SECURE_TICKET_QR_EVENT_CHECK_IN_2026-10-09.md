## Scope and architecture

- Existing backend `apps/api/src/modules/events/application/event.service.ts` already produced encrypted, HMAC-protected static ticket credentials, owner-scoped retrieval, delegated check-in role, a unique database `ticket_check_ins.ticketId` constraint and check-in transaction locks. This batch reuses those formats, secrets, models and endpoints; **no database migration was added**.
- `GET /v1/events/orders/:reference/tickets/:publicCode/credential` remains authenticated, limited to the customer's own **paid**, **active** ticket, now also requiring a published/sold-out event and active organizer. It retains `Cache-Control: no-store, private, max-age=0`, `Pragma: no-cache` and `Referrer-Policy: no-referrer`; view is audited without storing the bearer credential. Never return a QR payload from ordinary order listings or idempotency responses.
- `GET /v1/events/tickets/check-in/assignments` returns at most 100 eligible organizer-owned/delegated active-event summaries, not customer data or ticket secrets.
- `POST /v1/events/tickets/check-in` now requires an explicit UUID `eventId` in addition to a strictly formatted QR payload and optional request ID. The event must match the scanned ticket. The server derives staff identity from the opaque session; it checks original organizer and delegated **ACTIVE** `CHECK_IN` staff role, event/organizer statuses, **PAID** order, signed credential fingerprint, ACTIVE ticket and absence of prior check-in. Row locks serialize admission and staff revocation. A successful check-in and secret-free `EVENT_TICKET_CHECKED_IN` audit are created in one database transaction. Existing unique ticket-ID constraint prevents repeated scans. Never insert a ticket record or mark an unknown payment successful from QR input alone.
- Both QR read and check-in are **hard-stopped in production**, regardless of sandbox flags, and require `EVENT_TICKET_QR_SANDBOX_ENABLED=true` in nonproduction. The `.env.example` default stays **false**. The customer UI adds the distinct, independent default-off `VITE_TWIPAY_EVENT_QR_SANDBOX_ENABLED` switch; setting a UI flag never authorizes the backend.
- `apps/customer-ui/src/routes/dashboard/foundations/MyTickets.tsx` shows ordinary order history only, uses active/paid status and opens an on-demand `TicketQrPanel`. The panel renders the credential locally with pinned `qrcode` (`1.5.4`, typings `1.5.5`) without any server-side QR image endpoint; it hides after 60 seconds, on page hiding or on explicit dismissal. **The underlying ticket credential is static and remains a reusable bearer secret until checked in/invalidated**; hiding the UI does not rotate it and cannot prevent screenshots. Neither the raw payload nor rendered QR is put in React Query cache, browser storage, analytics, or downloadable files.
- `apps/customer-ui/src/routes/dashboard/foundations/EventCheckIn.tsx` provides an authenticated ErhaPay-styled staff page with hardware QR-scanner text entry and optional browser `BarcodeDetector` + `getUserMedia` camera scanning. Camera activation requires a user gesture and explicit permission; tracks are stopped after scanning, closing, errors and component teardown. Only an authoritative API `CHECKED_IN` response for the selected event is displayed as success. The scanner supplies an independent request ID and clears its transient input after submission; it never stores bearer credentials.
- `EventStaffManagement` connects existing event-owner routes to assign/revoke `CHECK_IN` staff, requiring existing active customers with verified **email**. Revoked assignments remain revoked and cannot silently regain access through another invitation. They never grant organizer financial/payout privileges.
- API adapter allowlist additions apply only to these exact authenticated paths; CSRF protection remains in place for mutations.

## Changes expressly not made

No payouts, financial-provider activation, ticket checkout activation, event publication activation, schema/ledger mutation, refund policy change, betting, new application, new customer design system or new ZIP-per-batch product. Ticket resale, transfers, refunds, check-in time windows, credential rotation, device trust and entrance offline mode require separate policy and real-world tests. The QR credential is a static single-use admission bearer token, not an expiring one-minute cryptographic token. A customer must keep it private and staff must check in online.
