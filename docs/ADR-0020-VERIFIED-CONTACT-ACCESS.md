# ADR-0020 — Phase 3.1: verified-contact access, not user lifecycle state

**Decision (2026-10-09):** Preserve `User.status=ACTIVE` for legitimate registrations and existing session/login rules. Define initial customer access as `emailVerifiedAt != null OR (phoneE164 != null AND phoneVerifiedAt != null)`. Collect no telephone number at initial signup. Email verification is therefore required for newly registered password users. `PENDING` is not repurposed.

A restricted session can call `/auth/me`, `/auth/csrf`, `/auth/mfa/status`, `/auth/mfa/challenge`, `/auth/contact/email/confirm`, `/auth/contact/email/resend`, and logout. All other controllers using `SessionAuthGuard` require contact verification **server-side**, and when the account has an active MFA credential they also require a recent MFA-authenticated server session. The small recovery exception set bypasses only these two access checks and retains CSRF + real session validation. This is an access gate, not a KYC, PIN, MFA, wallet, funding, bank or payment release approval. Existing default-off financial gates and provider qualifications remain unchanged.

Email codes: uniformly random six-digit OTP, HMAC-SHA256 using domain-separated server pepper, user + current email bound; ten-minute TTL, maximum five guesses per issued challenge, 60-second resend cooldown, ten challenges per account per rolling day, plus Fastify IP-based defense-in-depth (six mutations/minute, single-process only). Challenge generation, resend and confirmation serialize using the existing user row lock. Resend invalidates prior codes, successful confirmation atomically consumes all outstanding codes and sets the authoritative verified timestamp. Failed-attempt increments commit before the error is returned. Confirmation rotates the opaque session with MFA assurance reset; pre-existing login MFA must still complete. Dashboard identity reminders report a **verified BVN** as complete for the current funding-account prerequisite (a verified NIN alone is not sufficient for BVN-backed services); this summary is not a new financial authorization rule. Changing email later **must clear emailVerifiedAt and invalidate challenges in the same transaction**; contact-edit endpoints are deferred until this policy is implemented. No unauthenticated resend/confirm endpoint exists.

An encrypted notification is inserted in the same DB transaction as each challenge. Existing Resend provider and notification outbox perform best-effort dispatch and retry. `ACCEPTED` means provider accepted, not inbox delivered; otherwise the client displays a queued status and never claims delivery. No OTP or hash is returned to the browser or logged. Missing Resend settings do not transform a failed dispatch into verification success. The production environment must qualify distributed IP/device abuse defenses, email provider callback/delivery, PG/Redis concurrency and browser auth tests before rollout. Runtime financial operations remain default-off.

**Subsequent phases:** password recovery, verified contact edits, Google code+PKCE OIDC and identity-based account linking, expanded KYC and PIN-credential management in Phase 3; financial intent PIN/MFA/limits/holds enforcement in Phase 4. Do not activate legacy Firebase popup or local PIN state.
