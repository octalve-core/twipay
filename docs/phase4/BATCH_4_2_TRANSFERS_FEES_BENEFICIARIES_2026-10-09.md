## Source changes

1. `POST /v1/transfers/quote`: authenticated, sandbox-only bank account resolution and **server-calculated fee**; returns recipient name, masked account, payout amount, fee, exact total debit and a five-minute HMAC-signed quote. Token is bound to owner, provider, bank code, account fingerprint, resolved name, narration, amount, fee, total and expiry; it does not expose the account number, the PIN or bank resolver credentials. Dedicated `TRANSFER_QUOTE_HMAC_KEY` required. No client-supplied fee is trusted.
2. `POST /v1/transfers`: strict mandatory `quoteToken`, `expectedAccountName` and four-digit `transactionPin`; valid quote and total checked before PIN authorization, freshly checked after provider account resolution and again inside the debit transaction. The Phase 4.1 eligibility check receives **payout + fee**, ensuring transaction and daily limit checks include the actual debit. Provider payout receives **payout amount only**. One `approvalQuoteId` unique per transfer blocks quote replay under different idempotency keys; existing idempotency keys still govern safe retries. A changed quote, name, fee, amount, narration, owner or expired token cannot authorize a hold.
3. The financial record persists `amountMinor` separately from `feeMinor`. A wallet hold reserves the **total**. On verified provider success the journal debits the user wallet for total, credits provider clearing for payout and fee revenue for the fee. Failed outcomes release the full hold. Unknown/provider-unconfirmed outcomes retain the hold and go to reconciliation. A provider-confirmed reversal reverses the journal, including the fee. Existing ledger/journal invariants and fee arithmetic remain subject to real PostgreSQL/provider testing.
4. Owner-scoped saved bank-recipient endpoints: `GET/POST /v1/transfers/beneficiaries`, `PATCH/DELETE /v1/transfers/beneficiaries/:id`. Saving resolves the bank account from the selected sandbox provider and encrypts account data. Read responses are masked and do not contain ciphertext/fingerprints. Rename changes nickname only; remove is a soft archive, preserving past transfer records. Existing historical transfer-derived beneficiary records are not made user-saved automatically.
5. New transfers store recipient name, bank code and account last-four **immutable transaction snapshots**, so later beneficiary edits cannot rewrite the displayed recipient. Legacy records use the existing fallback. Transfer history/detail disclose exact fee and debit total; non-debit transaction types do not misleadingly claim a transfer debit.
6. Original ErhaPay withdrawal confirmation displays the server's payout amount, fee and total before collecting the PIN/consent. PIN stays in component memory, never the idempotency digest or browser storage. UI refuses unqualified provider flags, unavailable quotes, changed details, expired terms and ambiguous retries. The original saved-beneficiary page now lists masked records and offers provider-verified save, rename and archive. It accurately states that choosing a saved recipient as a transfer shortcut is not implemented yet.
